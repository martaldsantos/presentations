From scattered access to shared control

Direct integrations leave each application responsible for provider credentials, backend availability and usage controls. A gateway separates application logic from platform operations: applications integrate once; platform teams manage access, policies, models and tools centrally.

Cost + accountability

Combine quotas, caching and workload attribution to understand consumption and avoid unnecessary calls.

Capacity + continuity

Use multiple deployments, routing strategies and fallback without changing the application's endpoint.

Central governance

Keep provider credentials behind the gateway and apply common access and lifecycle controls.

Observable operations

Measure tokens, latency and outcomes before changing limits or architecture.

Approved agent tools

Expose a deliberate set of API operations through governed MCP endpoints.

One operating model

Connect identity, policy, routing and telemetry rather than treating them as isolated features.

One endpoint, one integration

The application calls the gateway instead of a provider directly. Backend credentials remain with the platform, not in application code.

01 / Centralise / 30 minPut the gateway in control

Replace direct model access with a governed endpoint. Before: application → provider endpoint and credential. After: application → gateway → model, with the provider credential held by the platform.

  1. Add a Foundry or custom model to your approved gateway configuration.
  2. Create a runtime access key or configure the authentication method supported by your deployment.
  3. Call the model through the gateway endpoint.
  4. Confirm that the application does not handle provider credentials.

Success: the same model response arrives through a new governed path.

02 / Control / 30 minManage AI consumption

Apply token and request guardrails by consumer. Use a trusted application identity as the counter key; a caller-controlled label alone is not an access boundary.

  1. Identify the consumer and decide whether limits belong to an application, user, workload or environment.
  2. Configure a small token-throughput limit that is easy to trigger.
  3. Generate repeated requests as app-a and inspect the enforced policy and response.
  4. Repeat as app-b and confirm an independent counter. Check the actual status codes for your chosen policy.

Try independent consumer counters

Illustrative simulation: a fixed 100-token session budget per application, with 40 tokens per request. This is not a real rate window or an Azure response.

app-a: 0 / 100 tokens | app-b: 0 / 100 tokens

Choose an application to send a simulated request.

Success: one consumer reaching its limit does not consume another consumer's allowance.

03 / Resilience / 30 minRoute across deployments

Keep the client endpoint stable while backend capacity or availability changes. A pool can combine a preferred deployment with alternate capacity; circuit-breaker and routing behaviour depend on the selected configuration.

  1. Create two approved model backends.
  2. Build a backend pool and route the API to it.
  3. Choose round-robin, weighted or priority-based routing based on the workload.
  4. Simulate a backend failure in a noncritical environment.
  5. Inspect routing outcomes, errors and recovery without changing the application URL.

Success: observed behaviour matches the intended fallback strategy. Consider retry safety, regional requirements and remaining capacity.

04 / Optimise / 25 minUse semantic caching

For appropriate repeatable prompts, look up a cached response using embeddings and similarity. A hit returns a cached result; a miss calls the model and can store the response.

  1. Baseline two similar prompts without caching.
  2. Configure cache lookup and response storage where supported.
  3. Compare latency and backend-call counts on hits and misses.
  4. Discuss similarity threshold, time-to-live and partitioning by consumer or context.

Guardrail: similarity does not guarantee correctness. Cached responses can be stale, unsafe or wrong for a different user or context. Do not share sensitive results across access boundaries.

Success: suitable repeated intent avoids a backend call without violating freshness, quality or isolation requirements.

05 / Observe / 25 minMake token use visible

Connect telemetry to workload accountability. Measure prompt, completion and total tokens alongside latency and request outcomes. Attribute usage to application, environment and workload.

  1. Enable supported gateway telemetry and configure its destination.
  2. Generate successful and policy-rejected requests.
  3. Inspect token metrics, latency, outcomes and consumer dimensions.
  4. Use the evidence to propose changes to quotas, architecture or cache policy.

Review logging configuration before capturing traffic. Prompts, responses and tool payloads may contain sensitive information.

Success: you can explain who consumed capacity and which control should change. Measure → understand → define policy → enforce → measure again.

06 / Govern / ExtensionPublish approved MCP tools

Expose only approved operations through a controlled Model Context Protocol (MCP) endpoint. Tool availability should reflect a deliberate approval and ownership process.

  1. Select one managed REST API and identify safe operations to expose.
  2. Create an MCP server using the selected operations where supported.
  3. Connect an MCP client, list the tools and invoke an approved operation.
  4. Inspect tool-call telemetry and discuss payload sensitivity.

Success: the client sees only the intended tools, access is controlled, and each tool has an owner and lifecycle plan.

Planning a guided session?

Prepare and validate the environment before the session. Suggested three-hour core path: context and validation (20 min), lab 1 (30 min), lab 2 (30 min), break (10 min), lab 3 (30 min), lab 4 (25 min), lab 5 (25 min), wrap-up (10 min). Schedule the MCP extension separately if more time is needed.

A pilot, not a production promise

Treat the dedicated AI Gateway tier and any preview capabilities as evaluation topics. Feature availability, APIs, regions, pricing, networking and service guarantees can change. Validate current support for your tier before provisioning or adopting any lab.

Verify current support

Check preview status, regional availability, limits and SLA terms. Do not assume a feature in one API Management tier exists in another.

Follow the whole data path

Assess gateway, model, cache and telemetry locations together. Gateway location alone does not establish data residency.

Start with a safe pilot

Choose a noncritical workload, confirm network and identity requirements, define success measures and keep a rollback plan.
