Part 1 / 00:12–00:18 / Dedicated-tier essentials

Three identities.
Do not confuse their credentials.

Administrator

Microsoft Entra ID

Sign in at ai.gateway.azure.com and manage resources using your permissions.

Application

Runtime access key

Send the gateway key in the api-key header. Issue a separate key per app and environment.

Gateway to backend

Managed identity or provider key

Configure backend authentication at the gateway. Applications do not receive provider credentials.

Preview runtime keys are gateway-scoped: every key reaches all published models and tools. Separate keys do not create per-asset permissions.

Speaker notes: Spend six minutes across runtime, policy and preview slides. Explain that management-plane Entra sign-in is not application runtime authentication. The overview documents gateway-scoped keys with no per-asset scoping yet. Use a gateway isolation boundary appropriate to the pilot and treat all runtime keys as secrets.
Part 1 / Dedicated-tier controls

Choose a policy card.
Select assets. Configure. Enforce.

Token rate limit / Models

Control token throughput using supported windows and counting dimensions. A blocked call returns 429.

Request rate limit / Models + tools

Control request volume per caller identity or IP address. A blocked call returns 429.

IP filter / Models + tools

Allow or deny client network ranges. A blocked call returns 403.

Content safety / Models + tools

Configure safety checks with an Azure AI Content Safety resource. A blocked call returns 400.

Source: policy scope, enforcement and runtime keys ↗

Speaker notes: Policies are configured with Type, Assets and Configure steps; no XML is required. Every applicable policy must allow the request. The governance guide describes token counting windows and dimensions; use the options actually available in the preview portal. Limits are operating controls, not authoritative billing. Honour Retry-After on 429 responses. Content safety needs its own resource and calibration, so it is optional in this PoC.

Part 2 / Models + runtime keys

Register the model.
Give the application a gateway key.

  1. Use Configure your gateway / Get started to discover Foundry accounts, or add a custom model.
  2. Choose backend key-based or managed-identity authentication; resolve verification warnings.
  3. Inspect imported models and record the exact, unique gateway model name.
  4. Use Keys / Create API key for one application and environment; store the key securely.

Part 2 / First model call / PowerShell example

Change the endpoint.
Keep provider keys out of the client.

$body = @{
  model = $env:AI_GATEWAY_MODEL
  messages = @(@{ role = "user"; content = "Explain an AI gateway briefly." })
} | ConvertTo-Json -Depth 4

Invoke-RestMethod -Method Post `
  -Uri "$($env:AI_GATEWAY_BASE_URL.TrimEnd('/'))/chat/completions" `
  -Headers @{ "api-key" = $env:AI_GATEWAY_API_KEY } `
  -ContentType "application/json" -Body $body

Set the three environment variables locally. Copy the exact OpenAI-compatible base URL from the gateway; use the registered model name.

Speaker notes: Run in a local terminal, not this webpage. AI_GATEWAY_BASE_URL is the full model base URL, for example https://<gateway>.azure-api.net/default/models/openai/v1. AI_GATEWAY_MODEL is the exact published model name. AI_GATEWAY_API_KEY is the app runtime key loaded from an approved secret store. This example is for a non-streaming OpenAI-compatible chat model, not Anthropic Messages API passthrough. Check a 200 response with choices/message/content; invalid key should fail with 401, a wrong model name should not silently route elsewhere. Do not log keys or sensitive response payloads.
Core PoC / Lab 1 / Governed access / 15 minutes

Put the gateway in control.

Before

Application → provider → model

The application handles provider endpoints and credentials.

After

Application → gateway → model

The gateway owns backend credentials and policy.

  1. Add a Foundry or custom model supported by your gateway.
  2. Configure runtime access using the supported authentication method.
  3. Call the model through the gateway.
  4. Confirm the application never handles provider credentials.

Success: same model response, new governed path.

Speaker notes: Compare the direct integration with the governed path. For a runtime-key-based deployment, create a lab access key. Never expose credentials in browser content, logs or public examples.
Core PoC / Lab 2 / Policy enforcement / 20 minutes

Control consumption
by consumer.

  1. Create separate runtime keys for app-a and app-b.
  2. Use Policies / Add policy; select a model and a small request or token limit.
  3. Count by caller identity; send requests with app-a until blocked.
  4. Repeat with app-b's key and inspect its independent allowance.

Observe enforcement

Allowed request → success
Rate-limited request → 429

Honour Retry-After. Use caller identity, not IP counting, for the two-application test.

Success: one consumer's exhausted allowance does not consume another's.

Speaker notes: Dedicated-tier policy cards use Type, Assets and Configure. Request and token rate-limit blocks return 429. Confirm which control rejected the call; backend throttling can also return 429. One key per application plus caller-identity counting demonstrates isolation of counters, not per-model authorisation. Runtime keys remain gateway-scoped. If the portal's preview options differ, inspect current documentation and record the discrepancy.

Core PoC / Lab 6 / Approved MCP tool / 20 minutes

Give agents approved tools.
Not unrestricted APIs.

  1. Choose a safe source. Use an approved remote MCP server or OpenAPI definition.
  2. Create the MCP server. Configure backend authentication and review its tool inventory.
  3. Connect an MCP client. Use the gateway's toolserver endpoint and runtime key; list tools and call one.
  4. Inspect telemetry. Validate the allowed operation and inspect policy and tool-call outcomes.

Success: controlled access, a deliberate tool inventory, and clear ownership.

Speaker notes: The dedicated tier supports remote MCP backends, OpenAPI definitions and built-in connectors; use one already approved source for this PoC. The endpoint follows .../toolservers/<server-name>/mcp; copy its exact URL from the portal. Backend authentication options include None, API Key, OAuth 2.0 and Managed identity as applicable. Restrict the source API or server before exposing it; do not assume keys provide per-tool scoping. Apply request rate limits to tools; token rate limits apply to models. Record who owns approval and lifecycle.
Part 2 / Evidence + closeout / 10 minutes

A successful PoC has evidence.
Not just a working demo.

Governed access

A real model call succeeds via the gateway. An invalid runtime key is rejected. No provider key is in the client.

Control + attribution

Limits reject excess traffic; app keys have independent counters. Token and latency telemetry is visible.

Tool + closeout

An approved MCP operation succeeds. Record gaps, owner and rollback; revoke lab keys and clean up approved lab resources.

Capture sanitised results, not secrets. Decide whether to proceed, change the design or stop.

Speaker notes: Record response status, policy identity and timestamps; confirm rate-limit errors originate from the intended control rather than only from the backend. Check the telemetry destination, model/tool inventory and gateway-wide key scope. Do not delete shared model, telemetry or tool resources: clean up only resources explicitly created for this pilot and approved for removal. A failed criterion is a reported gap, not a passed PoC. No production migration is implied.
