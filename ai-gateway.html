Lab 1 / Centralise / 30 minutes

Put the gateway in control.

Before

Application → provider → model

The application handles provider endpoints and credentials.

After

Application → gateway → model

The gateway owns backend credentials and policy.

  1. Add a Foundry or custom model supported by your gateway.
  2. Configure runtime access using the supported authentication method.
  3. Call the model through the gateway.
  4. Confirm the application never handles provider credentials.

Success: same model response, new governed path.

Speaker notes: Compare the direct integration with the governed path. For a runtime-key-based deployment, create a lab access key. Never expose credentials in browser content, logs or public examples.
Lab 2 / Control / 30 minutes

Control consumption
by consumer.

  1. Identify the caller using a trusted consumer identity.
  2. Apply a small token or request limit.
  3. Generate requests as app-a until the policy enforces it.
  4. Repeat as app-b and confirm an independent counter.

Independent counters

app-a → allowance A
app-b → allowance B

Inspect the real policy response. Rate and quota policies can enforce different limits and status codes.

Success: one consumer's exhausted allowance does not consume another's.

Speaker notes: A caller-controlled app label alone is not a security boundary. Bind the counter key to validated identity. Discuss scope and enforcement windows. Observe actual status codes for the selected policy rather than assuming all restrictions produce the same response.
Lab 3 / Resilience / 30 minutes

Backend capacity changes.
The client endpoint does not.

Application

Same gateway URL

AI gateway

Backend pool + routing strategy + circuit breaker

Deployments

Primary capacity
Secondary / alternate capacity

Create two backends → build a pool → route the API → simulate a failure → inspect recovery

Design decision: round-robin, weighted or priority-based routing?

Speaker notes: Test only in a noncritical environment. Verify the chosen tier's pool and circuit-breaker support. Consider retry safety, data residency, remaining capacity and what happens when all backends fail. Success means observed behaviour matches the intended strategy, not a promise of zero downtime.
Lab 4 / Optimise / 25 minutes

Avoid paying for
the same intent twice.

Lookup

Prompt + similarity

Look for an appropriate cached response using embeddings.

Hit

Return cached response

Avoid another model call when reuse is safe.

Miss

Call model + store

Generate a response and cache it where appropriate.

Baseline similar prompts → configure lookup + store → compare latency and backend calls

Similarity is not correctness. Discuss threshold, TTL and partitioning; cached results can be stale, unsafe or wrong for another context.

Speaker notes: Choose repeatable, nonsensitive prompts. Compare quality as well as performance. Do not reuse sensitive responses across consumer or access boundaries. Verify cache support and its data location for the chosen tier.
Lab 5 / Observe / 25 minutes

Make consumption visible.
Then make decisions.

Measure

Tokens + performance

Prompt, completion and total tokens. Latency and request outcomes.

Attribute

Workload accountability

Application, environment and workload dimensions.

Act

Evidence-led policy

Adjust quotas, architecture and cache policy based on observed behaviour.

Measure → understand → define policy → enforce → measure again

Review logging before capturing traffic. Prompts, responses and tool payloads may contain sensitive information.

Speaker notes: Configure a supported telemetry destination. Generate successful and rejected requests, then explain who consumed capacity and which control should change. Telemetry support and token accounting vary by integration.
Lab 6 / Govern tools / Extension

Give agents approved tools.
Not unrestricted APIs.

  1. Choose a managed REST API. Select safe operations for tool exposure.
  2. Create the MCP server. Expose only the approved operations where supported.
  3. Connect an MCP client. List tools and invoke one through the governed endpoint.
  4. Inspect telemetry. Review tool-call traffic and payload sensitivity.

Success: controlled access, a deliberate tool inventory, and clear ownership.

Speaker notes: MCP means Model Context Protocol. Tool approval does not replace per-operation authorisation. Discuss who approves tools, manages changes and owns retirement. Verify current MCP support before the exercise.
